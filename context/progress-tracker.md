### MCP endpoint burst rate limiting (this session)

- **User concern**: the MCP Streamable-HTTP endpoint (`src/app/api/mcp/[projectId]/route.ts`) is hit by external clients on every tool call, authenticated via bearer API key rather than a session. The only existing throttle was `requireUnderLimit`'s **monthly** quota (`organization.mcpRequestsLimit`, counted from `mcpRequestLog` rows) — nothing limited burst/rapid-fire calls within a short window, so a compromised key or buggy/malicious client could hammer the endpoint (each call already costs several Postgres round-trips before any MCP logic runs).
- Confirmed the codebase already has **Arcjet** (`@arcjet/next`, `@arcjet/ip`) installed and used for exactly this in `src/app/api/auth/[...all]/route.ts` (sign-up/sign-in `slidingWindow` rate limiting), with `ARCJET_KEY` already configured (`src/config/url.config.ts`, `.env.example`) — no new infra (Redis/Upstash) needed.
- Added a `slidingWindow` Arcjet rule to the MCP route, keyed by `apiKeyId` (not IP, since a key is pinned to one IP only after first use and grants may be exercised before that pin exists) — `max: 60`, `interval: '1m'` (confirmed with the user). The check runs in `authenticate()` right after the key is verified/matched to the project, before the monthly-quota DB counts and the `allowedIp`/`lastUsedAt` writes, so a throttled request short-circuits before the more expensive work. Denied requests get a `429`.
- `pnpm tsc --noEmit` passes with zero errors. **Not yet manually verified** — would need a live test API key hammered with ~70 rapid requests in a minute to confirm the 429 kicks in around request 61 and normal single-call usage is unaffected.

### Real in-app subscription upgrade/downgrade with proration (this session)

- **Problem**: "Upgrade" always opened a brand-new Creem-hosted checkout for the target plan's product, never touching the customer's existing subscription (so proration behavior was whatever Creem's checkout flow does implicitly — undocumented, and the old subscription wasn't referenced/canceled). "Downgrade" just opened Creem's hosted customer portal with no target plan communicated. Investigated whether this project uses Stripe (it doesn't, despite `stripe` sitting in `package.json` — billing is 100% Creem via `@creem_io/better-auth`) and whether Creem itself has a real update-in-place + proration primitive (it does: `creem.subscriptions.upgrade(subscriptionId, { productId, updateBehavior })`, part of the `creem` npm package which is already a transitive dep, already imported directly in `src/app/api/billing/invoices/route.ts`).
- **New route** `src/app/api/billing/change-plan/route.ts` (`POST`, `withWorkspace` + `requiredPermissions: ['billing.write']`): resolves the target Creem product id from `PLANS`, looks up the org's active `Creem_subscription` row (`referenceId`/`status: 'active'`), calls `creem.subscriptions.upgrade(sub.id, { productId, updateBehavior })` — `proration-charge-immediately` for upgrades, `proration-charge` (credit applied to next invoice, no immediate refund) for downgrades via `isDowngradePlan` — then writes the new plan/limits to `Organization` directly rather than waiting on the async webhook. Returns a `no_active_subscription` 409 if the org has never subscribed (Free plan) — that case still needs the checkout flow to collect a payment method.
- **New shared helper** `src/lib/billing/apply-plan-to-organization.ts` (`applyPlanToOrganization`) — extracted the previously-duplicated (3x) "compute limits from `PLANS` and write to `Organization`" block out of `src/lib/auth/auth.ts`'s Creem webhook handlers, now reused by both the webhook handlers and the new route so both code paths stay in sync.
- **Fixed a latent correctness bug while doing this**: `onSubscriptionActive`/`onSubscriptionUpdate`/`onSubscriptionPaid` in `auth.ts` previously derived `planName` solely from `metadata.planName`, which is only set once at original checkout creation. Neither `subscriptions.upgrade()` nor `subscriptions.update()` accepts a `metadata` field, so a subscription changed via the new direct API call keeps stale metadata — the later `subscription.update` webhook would have read the *old* plan name and silently overwritten the correct one the new route just set. Fixed by adding `resolvePlanNameFromEvent()` in `auth.ts`, which resolves the plan from the webhook payload's live `product.id` (via the pre-existing `getPlanAndTierFromPriceId`) first, falling back to `metadata.planName` only if that lookup fails. This makes plan resolution correct regardless of which flow (checkout, portal, or the new direct API call) changed the subscription — not just a fix scoped to this feature.
- `src/features/billing/components/upgrade/upgrade-view.tsx`: new `handleChangePlan()` posts to the new route (with a plain `window.confirm()` proration disclosure — "charged immediately" for upgrades, "credited next invoice" for downgrades — since Creem has no proration-preview endpoint to build a real preview against) and calls the pre-existing `useWorkspaceStore().refreshActiveWorkspace()` on success so the UI reflects the new plan without a page reload. The button now calls `handleChangePlan` (both directions) whenever the org already has an active paid (non-Free) subscription, and only falls back to the old `handelSubscriptions` checkout flow for a genuine first-time subscribe. `handlePortal` (Creem hosted portal) was removed from this file entirely since it's no longer used here — `subscription-menu.tsx`'s own portal usage (payment method management) is untouched.
- `pnpm tsc --noEmit` passes with zero errors. **Not yet manually verified in the browser/against Creem test mode** — would need a workspace with an active test-mode paid subscription to click through an actual upgrade and downgrade and confirm the Creem test dashboard shows the subscription's product changed in place with a prorated transaction, per the plan's Verification section.
- **Bug found and fixed while debugging a live 409 from this route** (`no_active_subscription` for an org that clearly had one): the new route's lookup assumed `creem_subscription.referenceId === Organization.id`, copied from the existing (also-affected) pattern in `invoices/route.ts`. Queried the real DB directly (via a scratch `pg` script, since the Prisma client here is TS-only/bundler-targeted with no `tsx`/`ts-node` in the project) and confirmed `referenceId` is actually the Creem **user** reference (the better-auth session user id), never the organization id — e.g. a Pro-plan org's 4 subscription rows all had `referenceId: 'ajEPJZ1ZGwU8Oos18lRKyJKu815CrIpi'` (the owning user's id), not the org's id. The reliable join is `creem_subscription.creemCustomerId === Organization.creemId` instead. Fixed both `change-plan/route.ts` and `invoices/route.ts` (which had the identical bug and was almost certainly returning an empty invoice list for every real org before this) to join on `creemCustomerId`.
- **Second bug found immediately after, same root cause class** — fixing the 409 surfaced a live 404 from Creem (`"Subscription does not exist"`) because `change-plan/route.ts` was calling `creem.subscriptions.upgrade(activeSubscription.id, ...)` using `Creem_subscription.id`, which is a locally-generated Prisma PK, not Creem's real subscription id (that's the separate `creemSubscriptionId` column, e.g. `sub_25CdQOS5I5XyQo2ejRCNHe`). `invoices/route.ts` had this exact same mix-up baked in too (matching `creemSubMap.get(inv.id)` where `inv.id` was the local PK) — its enrichment lookup was silently failing on every real subscription (falling back to unenriched local data with `amount: null`), which is presumably why it went unnoticed. Fixed `change-plan/route.ts` to call `creem.subscriptions.upgrade(activeSubscription.creemSubscriptionId, ...)`, and fixed `invoices/route.ts` to match Creem's live subscriptions on `creemSubscriptionId` while keeping `sub.id` only as the invoice's local display id. **Lesson for future billing work here**: `Creem_subscription` has three different-looking id-ish fields (`id` = local PK, `creemCustomerId` = Creem customer, `creemSubscriptionId` = Creem subscription) that are easy to conflate — verify against real DB rows before trusting which one a given Creem API call needs, don't infer from existing code that may itself have never been exercised against live data.
- **Third bug, found after the 404 fix**: Creem then rejected the upgrade with `"This subscription must be active before it can be modified"` even though the chosen local row had `status: 'active'`. Queried Creem's live API directly (`creem.customers.listSubscriptions`) for the test customer and found the local `creem_subscription` table is unreliable for deciding modifiability — it had two rows for the *same* `creemSubscriptionId` with conflicting statuses (`active` vs `canceled`, near-identical timestamps; webhook events are persisted as new rows, not upserted). Worse, live Creem data showed **three separate concurrently-active subscriptions** for the same customer, all on the Pro product — direct proof of the exact problem this feature set out to fix: the pre-fix "always open a new checkout to upgrade" flow left multiple simultaneous active subscriptions instead of modifying one in place (in production this would mean triple-billing). Rewrote `change-plan/route.ts` to stop trusting the local table's `status` entirely and instead call `creem.customers.listSubscriptions(org.creemId)` live, filter to `status === 'active'`, and pick the most recently created one (`createdAt` desc) as the subscription actually in effect.
- **Verified end-to-end against live Creem test data, then cleaned up test debris**: a Pro→Business upgrade correctly charged $29.82 (prorated) to the subscription's `lastTransaction`, confirming proration genuinely works. Two leftover duplicate active $19 Pro subscriptions from before the fixes above (`sub_4u220csL2NKd3USH0Gjm6B`, `sub_2D717yDgyw99ksYtI7SWmQ`) were canceled via `creem.subscriptions.cancel(id, { mode: 'immediate' })`, at explicit user confirmation naming both ids, leaving the test customer with exactly one active subscription.
- **User then reported a Business→Advanced upgrade "didn't ask for payment"** — checked live Creem data again and confirmed a real transaction (`tran_2u9nOUbb0r8QiOUpsBqPok`, $39.71, `status: "paid"`) had in fact been charged; this is expected, not a bug — the new flow charges the payment method already on file via Creem's API directly (like Stripe/Chargebee subscription updates), unlike the old flow which always redirected to a hosted checkout page to collect a *new* card. The UX gap was that nothing in the app surfaced the charged amount. Fixed: `change-plan/route.ts` now captures `updatedSubscription.lastTransaction` from the `subscriptions.upgrade()` response and returns `{ charge: { amount, currency, status } }` (only for the immediate-charge/upgrade path — a downgrade's `proration-charge` behavior defers to the next invoice, so there's no new transaction to report yet). `upgrade-view.tsx`'s `handleChangePlan` now shows a `sonner` `toast.success` with the formatted charged amount ("Switched to Advanced — $39.71 charged to your card on file"), or a "credit applies to your next invoice" toast for downgrades.
- **Flag for later**: the underlying duplicate-active-subscriptions data problem (in Creem itself, for any customer who upgraded before the third-bug fix shipped) isn't retroactively cleaned up by the code changes — only the one test customer above was manually cleaned up this session. Any other pre-existing customer in the same state would need the same one-off cancellation.
- **Explicit user request**: show the exact dollar estimate *before* committing to a plan change, not just a toast after the fact. Since Creem has no proration-preview API (confirmed — no `preview`/`estimate`/`quote` method anywhere in the `creem` SDK), built our own estimate: new `POST /api/billing/change-plan/preview` (`src/app/api/billing/change-plan/preview/route.ts`) replicates Creem's apparent linear time-based proration — `(targetPriceCents - currentPriceCents) * remainingFraction`, where `remainingFraction` comes from the live subscription's `currentPeriodStartDate`/`currentPeriodEndDate` vs. now. ### Security review of the billing/subscription system, per explicit user request (this session)

- **Critical finding: cross-tenant IDOR in `src/lib/auth/workspace.ts`'s `withWorkspace`**, pre-existing and not introduced by the billing work above, but directly exploitable through it. `withWorkspace` computes `role`/`permissions` from the caller's own `session.activeOrganizationId`, then lets `workspaceId` be silently overridden by a `?workspaceId=` query param (or `params.idOrSlug`) **without ever re-validating that the caller belongs to that other org** — the `requiredPermissions`/`requiredRoles` checks run against the stale role from the caller's *own* org, not the target. Confirmed no other layer catches this (no `middleware.ts` exists; `withAuth` in `src/lib/api/base-handler.ts` only checks "is there a valid session," nothing about org membership). Concretely: any authenticated user who is `owner`/`moderator` of *any* org (even one they just created for free) could call `POST /api/billing/change-plan?workspaceId=<victim-org-id>` and have it charge the victim org's real Creem subscription — and `GET /api/billing/invoices` was even more exposed, since it passed **no** `requiredPermissions` at all, so *any* logged-in user regardless of role could read *any* other org's invoice/payment history via the same trick. This is a systemic bug affecting every route built on `withWorkspace` (Projects, Contexts, MCP, Activity, etc.), not just billing — flagged to the user as a much larger follow-up decision, out of scope for this pass.
- **Fix applied (user-approved scoped patch, not a `withWorkspace` rewrite)**: added an explicit `if (workspaceId !== activeOrganization?.id) return 403` guard to all four `/api/billing/*` routes — `change-plan/route.ts`, `change-plan/preview/route.ts`, `invoices/route.ts`, `resource-usage/route.ts` — refusing to act on any workspace other than the caller's own active one, regardless of what `?workspaceId=` claims. This closes the exploit path for billing specifically; the general `withWorkspace` bug remains unfixed everywhere else in the app pending a separate decision from the user (bigger blast radius — role/permissions would need to be recomputed against the resolved `workspaceId`, not the session's active org).
- **Medium finding, fixed**: `applyPlanToOrganization`'s default `resetUsageWindow: true` was firing on *every* plan change, including downgrades and lateral moves (e.g. toggling monthly↔yearly on the same tier) — and resource quotas (`getWorkspaceResourceUsage`) count items created since `lastResetDate`, so a paying customer could cheaply/repeatedly reset their resource-creation quota by toggling plans back and forth instead of waiting for a genuine billing-period renewal. Fixed by passing `resetUsageWindow: false` from both `change-plan/route.ts`'s call and `auth.ts`'s `onSubscriptionUpdate` handler (the generic "subscription changed" webhook, which fires for any plan swap — checkout, portal, or the new direct API — not specifically a renewal). Left `resetUsageWindow: true` (the default) on `onSubscriptionActive` (brand-new subscription) and `onSubscriptionPaid` (genuine renewal invoice) — those two are the only events that legitimately represent "a new billing period started."
- **Low findings, not yet fixed (reported, no action taken)**: (1) no idempotency/lock on `change-plan` — two concurrent/duplicate requests could both pass the active-subscription check and both trigger a proration charge; the frontend only disables the button after click, which isn't a reliable guard against replay/multiple tabs. (2) `change-plan`/`preview` accept any `PLANS` entry found by name rather than checking against `SELF_SERVE_PAID_PLANS` explicitly — currently safe only because Free/Enterprise happen to lack `price.ids`/a numeric price, an implicit rather than enforced guarantee.
- `pnpm tsc --noEmit` passes after all four route patches.

### Pending-cancellation plan changes now resume the subscription instead of 409ing (this session)

- **User question, not a loophole this time**: "if I cancel a plan (scheduled for period-end) and then try to upgrade/downgrade before that, what happens?" Investigated and found a real functional gap: Creem subscriptions move to a distinct `scheduled_cancel` status once cancellation is scheduled (not just `active` + a `cancelAtPeriodEnd` flag — confirmed via the SDK's `SubscriptionStatus` enum and the `resume()` method's own doc comment, "must be in paused or scheduled_cancel status"). `getActiveCreemSubscription()` filtered strictly to `status === 'active'`, so once a cancellation was pending, both `change-plan` and its `preview` route returned a 409 `no_active_subscription` — fully blocking the user from changing their mind, with no in-app path other than going to Creem's hosted portal to resume first.
- Fixed: `getActiveCreemSubscription` (`src/lib/billing/creem-client.ts`) now also matches `scheduled_cancel`, not just `active`. `change-plan/route.ts` explicitly calls `creem.subscriptions.resume(activeSubscription.id)` before `subscriptions.upgrade()` when the found subscription is `scheduled_cancel` — using the documented `resume()` method rather than relying on `upgrade()`'s undocumented behavior on a canceling subscription. `change-plan/preview/route.ts` now returns `pendingCancellation`/`cancelDate` so the confirmation modal can warn the user *before* they commit that switching plans will resume billing, rather than resuming it as a silent side effect — `change-plan-confirmation-modal.tsx` shows an amber warning block and relabels the confirm button "Resume & switch plan" in this case.
- `applyPlanToOrganization` (called after the upgrade succeeds, unchanged) already unconditionally clears `subscriptionCanceledAt`/`subscriptionEndsAt` on every call, so no changes were needed there — the local DB naturally reflects "no longer pending cancellation" once the resume+upgrade completes.

### Cancel-subscription button was failing with "Subscription cannot be canceled in state: canceled" (this session)

### Version history redesign: "Main" pointer model (git-branch style)

- User wanted a different mental model after seeing the first version: pick any version from a dropdown, preview it, and flag it **Main** without creating a new version number or renumbering anything — closer to moving a git branch ref than to a linear revert.
- Added `Context.mainVersionId String? @unique` + `mainVersion ContextVersion? @relation("ContextMainVersion", ...)` (and the opposite `ContextVersion.mainForContext Context? @relation("ContextMainVersion")`), decoupling "the highest version number ever created" (the `version` counter, monotonic, unaffected by Main changes) from "which version is currently active" (`mainVersionId`, a movable pointer). Pushed via `db push --accept-data-loss` (flagged only because of the new unique constraint on existing rows, which just get `NULL` — confirmed with the user before running, since the harness blocks `--accept-data-loss` without explicit approval).
- Setting a version as Main copies that snapshot's `title`/`description`/`content` onto the live `Context` row (so the app actually serves that content) and repoints `mainVersionId` — but does **not** create a new `ContextVersion` and does **not** touch `version`. A normal content edit still creates a new `ContextVersion`, but as of the row below no longer auto-repoints Main at it.
- **Removed the "a fresh edit becomes Main automatically" behavior described in the row above** — user reported this was unwanted: saving an edit (from `ContextForm`, including plain title/description edits via `ContextDetailsModal`, since both go through the same PATCH branch) should only ever create a version snapshot; Main must always be moved manually via "Set as main version" in the history modal, never implicitly. Concretely, `patchHandler` in `.../contexts/[contextId]/route.ts` still writes the `ContextVersion` row and bumps `version`, but the `tx.context.update` no longer spreads `...data` or sets `mainVersionId` — only `updatedById`/`version` change. - API: `.../versions/[versionId]/restore` renamed to `.../versions/[versionId]/set-main` (same `canManageProject` gate). - `context-version-history-modal.tsx` rewritten: a `Select` dropdown (not a scrollable row list) picks a version, its content previews below via `RichTextViewer`, and (for `canManage` users) "Set as main version" + "Delete version" buttons act on whatever's selected. Confirmed via grep that `_count.members` had exactly one producer (this route) and one consumer (this card) before changing the shape — `archived-project-card.tsx` never rendered a count at all.

### MCP requests/month subscription limit (this session)

- New `Organization.mcpRequestsLimit` (`Int? @default(5000)`) follows the exact same shape as every other `xLimit` field, plumbed through the same four places the others already touch: the better-auth `additionalFields` schema and both Free-downgrade webhook handlers in `src/lib/auth/auth.ts`, `FREE_PLAN_DEFAULTS` (`pricing-plan-taglines.ts`), `PlanDetails['limits'].mcpRequests` per plan in `pricing-plans.tsx` (Free 5,000 / Pro 100,000 / Business 300,000 / Advanced 500,000 / Enterprise `INFINITY_NUMBER`), and `apply-plan-to-organization.ts`.
- `McpRequestLog` (already existed, write-only, one row per MCP call storing `receivedAt` always + `respondedAt` only on success) gained a denormalized `organizationId` column with its own `[organizationId, receivedAt]` index, since the limit check runs on every MCP request (much hotter than any other limit check) and joining through `projectId` → `Project.organizationId` on every call wasn't worth it when the org id is already in hand from the project lookup in `authenticate()`.
- Enforced in `src/app/api/mcp/[projectId]/route.ts`'s `authenticate()`, right after the project lookup and before IP-pinning (fail fast, no writes if already over limit). Returns **HTTP 429** with `code: 'limit_reached'` — the shared `requireUnderLimit` helper (`src/lib/api/plan/require-under-limit.ts`) gained an optional `status` param (default 400, unchanged for all 9 existing call sites) instead of forking a second helper.
- **Counting unit is 2 per successful call, 1 per failed call** — explicit user requirement ("request AND response both count, together"): a request that never gets a response (thrown error) only consumes 1 unit. Computed as `count(receivedAt >= periodStart) + count(respondedAt IS NOT NULL AND receivedAt >= periodStart)`, summed — not a single `count()` — both in the enforcement check and in `get-workspace-resource-usage.ts`'s new `mcpRequests` usage item (surfaces automatically on the existing `/api/billing/resource-usage` UI, no new frontend component).

## Architecture Decisions

| Decision | Reason |
|----------|--------|
| Projects are per-project ACL (`ProjectMember`), not just workspace-role-gated | User feedback: a project must be invisible to a workspace member until explicitly granted access, so workspace `member`/`viewer` roles alone aren't enough. |
| Org `owner`/`moderator` implicitly bypass `ProjectMember` and see all projects | Standard admin override — avoids needing to backfill `ProjectMember` rows for every project whenever an org admin needs access. |
| Project write authorization is enforced inline via `src/lib/permissions/project-access.ts`, not by extending Better Auth's access-control statements | Keeps `src/lib/permissions/workspace-permissions.ts` and `src/lib/auth/auth.ts` untouched, per the task's "do not rebuild auth" constraint. |
| Used `prisma db push` instead of `prisma migrate dev` for the new models | This project has no `prisma/migrations` history (schema was managed via `db push`); running `migrate dev` for the first time would have required a full database reset, which risks dropping existing data. `db push` applies the new tables additively without that risk. |
| Projects list is a card grid, not a data table | Matches the plan's chosen UX (Linear/Notion-style) for a small number of top-level entities that are primarily "click to open," vs. the dense row-based `MemberTable` pattern used for workspace members. |
| **(Supersedes the first row above)** Project management (create, settings, member management, and — once built — asset creation inside a project) is now gated on org-level `owner`/`moderator` only, not per-project delegated ownership | Explicit user requirement: "No one except the owner and moderator of the organization will be able to create projects... access settings... create assets." `canManageProject()` in `project-access.ts` now checks `isOrgAdmin` instead of `role === 'owner'`. `ProjectMember.role` `'owner'` is retired as an assignable value (Zod enums narrowed to `member`\|`viewer`); read-level `ProjectMember` access (a project is invisible until granted) is unchanged — this only tightens *management*, not visibility. **Important for future work**: when Contexts/Instructions/Skills/etc. get real CRUD (currently `PlaceholderTab` stubs), asset creation inside a project must also be gated on `isOrgAdmin`/`canManageProject`, per this same requirement — don't default to allowing any project member to create assets. |
| Context (and future resource type) writes reuse `canManageProject` (org admin only) rather than a separate looser permission | Applying the row above literally — asset creation is project management, not a `ProjectMember` privilege. A `canWriteProjectResource` helper that allowed any non-viewer member to write was implemented first and reverted before shipping. Read access for Contexts stays open to any project member (including `viewer`), per task 003's explicit MVP permissions note ("assume authenticated project members can access Contexts"). |
| Context delete is a hard delete, not soft delete | Task 003's doc suggested soft delete, but Project already reversed soft delete for lack of a recovery/trash UI (see the delete/archive redesign row above). Asked the user directly rather than re-litigating the same mistake; they chose hard delete for consistency. |
| Context content is stored as Tiptap-produced HTML (`String @db.Text`), not Markdown or Tiptap JSON | Simplest format for both the editor (`editor.getHTML()`) and read-only rendering (`dangerouslySetInnerHTML` in `RichTextViewer`) with no separate parse/serialize step. `react-markdown` (pre-existing dependency) is unrelated — it's not used for Context content. |
| `RichTextEditor`/`RichTextViewer` live in `src/components/editor/`, not `src/features/contexts/` | Task 003 explicitly requires the editor be reusable by future resource types ("Do not create a Context-specific editor") — placing it under a shared component path (not a feature folder) makes that reuse the default rather than something to refactor later. |
| Context version history was added despite task 003 explicitly deferring it | Direct user request after shipping — asked "how do I switch to a previous version" and wanted the ability to set any prior version as current. Confirmed scope directly with the user (every-edit snapshots, restore-as-new-version) rather than guessing, since the task doc's deferral made this an out-of-band addition. |
| Restoring a version always creates a new version rather than rewriting history in place | User's explicit choice when asked — keeps version numbers strictly increasing and history append-only, so nothing is ever lost even if a "wrong" restore happens. |
| Instructions, Skills, Prompt Templates, and Checklists were built via scripted find/rename/sed cloning of the Context feature's files, not hand-written | The four types are structurally identical to Context (same models, same API shape, same components) — cloning mechanically is faster and less error-prone than re-typing ~90 near-duplicate files by hand, as long as the clone is verified (`tsc` + curl) before moving to the next type. Instructions was built first and checked before repeating for the rest. |
| Checklists store content as the same markdown field as the other types (GFM task-list syntax), not a separate structured item model | Explicit user decision when asked — keeps 4 of the 5 new resource types byte-for-byte identical in architecture rather than forking a bespoke checklist-item UI/schema for a cosmetic difference. |
| Agent Profiles have no version history and no long-form content field, unlike the other 5 resource types | Explicit user decision — an Agent Profile is a container that bundles references to *other* resources (which already have their own versioning), not authored content of its own. Editing an Agent Profile updates the live row directly, same as a status flip elsewhere. |
| `AgentProfileResource.resourceId` is a polymorphic reference with no DB-level foreign key | A single FK can't span 5 different tables (Context/Instruction/Skill/PromptTemplate/Checklist). Resolved in application code (`resolve-agent-profile-resources.ts`, batched `findMany` per type) instead; a reference to a since-deleted resource resolves to `null` rather than erroring, since the other resource types use hard delete and there's no cascade cleanup across the polymorphic boundary. |
| Building Instructions/Skills/Prompt Templates/Checklists/Agent Profiles was scoped to just those five features, deliberately excluding a category-based starter-template/seeding system | User explicitly deferred the seeding system to a later phase when asked — avoids half-finishing an onboarding flow in the same round as the core CRUD features it would depend on. |
| Approvals dropped entirely (nav item, route, and doc references removed rather than built) | Explicit user decision: only org owner/moderator can ever touch content (create/edit/publish/set-main), so there's no distinct "submitter" role for a separate approve/reject step to review — publishing is already a direct, single-party org-admin action. |
| Activity uses a new dedicated `ProjectActivity` model, not the pre-existing workspace-scoped `Audit` model | User's explicit choice when asked. `Audit` is keyed by `workspaceId` (not `projectId`) and has exactly one call site (`organizationHooks.afterUpdateOrganization`) — extending it to project-scoped events would couple two otherwise-unrelated systems. `ProjectActivity` intentionally omits IP/user-agent fields that `Audit` carries — it's a product-facing feed, not a security audit log. |
| MCP auth is a per-project `ProjectApiKey` (bearer token), not Better Auth's unused OAuth `mcp` plugin (present in `node_modules`, never enabled) | Simpler for a project-scoped MVP — static bearer tokens are how most remote MCP servers (Notion, Linear) authenticate today; the OAuth plugin would need new `oauthApplication`/`oauthAccessToken`/`oauthConsent` tables plus an authorize/consent UI for no stated requirement. |
| MCP keys are scoped to individually-picked resources — there is no "unscoped, sees everything published" key | Explicit user requirement: a key must be excludable from specific resources (e.g. a "marketing" Context) rather than blanket-exposing every published resource in the project. A whole Agent Profile can also be granted directly, which implicitly grants read access to that profile's bundled resources too. **Superseded by the next row** — this scoping now lives on the `McpIdentity`, not the key itself. |
| MCP access is modeled as a first-class `McpIdentity` (org-scoped service account, no login of its own) rather than resources picked ad hoc per key | Replaced the original per-key `ProjectApiKeyResource` design the same session it was built, before real usage — user clarified the actual need was "an org owner/moderator creates a user, grants it into specific projects with specific resource permissions, and it has no organization access at all — the only thing that exists for it in practice is an MCP key." A key is now just a bearer credential for an identity; `resolveApiKeyGrants` resolves what it can see *live* from the identity's current grants, so permission changes take effect on existing keys instantly, with no revoke-and-reissue needed. |
| **(Reverses the original "GitHub-PAT style, shown once" design)** `ProjectApiKey.secret` now stores the raw key permanently instead of only a `keyHash`, so it can be re-copied into a full MCP config later | Explicit user decision: only `canManageProject` (org owner/moderator) callers can ever see it — enforced server-side in both `GET .../mcp/keys` and `GET .../mcp/identities`, not just by hiding the UI button — and the user's reasoning is that the owner is the one who hands the config to teammates anyway, so persisting it for that specific, already-trusted caller adds no real exposure. Keys created before this migration have `secret: null` forever, since their raw value genuinely was never captured; they fall back to the `<your-api-key>` placeholder in "Copy configuration" until reissued. |
| Library syncs all 7 of awesome-copilot's resource folders (instructions/agents/skills/workflows/cookbook/plugins/hooks), not just the 3 that map cleanly onto existing resource types | Explicit user decision when asked — user wanted every category available from the local database, not fetched live from GitHub per browse/import. Bundle folders (plugins/hooks/skills) each still collapse to one cached row via a single primary doc, so the cache stays one-row-per-item regardless of source structure. |
| `agents/` defaults to Prompt Template, `workflows/`+`hooks/` default to Skill, `cookbook/` defaults to Prompt Template, `plugins/` defaults to Context — all just pre-fills, never enforced | Explicit user decision when asked. No source category maps to Agent Profile, since that resource type has no content field to receive imported text at all. |
| `LibraryTemplate` is a bare read-only cache with no FK to/from the 5 resource tables, and attribution is a content-only footer rather than a schema column | Keeps import a one-way copy — deleting/refreshing the cache can never cascade into or orphan a reference on an already-imported project resource, and no schema change was needed on any of the 5 existing resource types to ship this feature. |
| Manual library resync (`POST /api/library/sync`) is gated by the existing `isOrgAdmin` check rather than a new system-admin permission | Explicit user decision when asked. No server-side "platform admin" concept exists anywhere in the codebase yet (the `system-admin/*` nav is only ever gated client-side); introducing one for a single low-stakes, idempotent, once-daily-anyway action wasn't justified. |
| Library has two import entry points sharing one backend, not one generic modal | Explicit user request: a "Use template" action on each resource type's list page (project + type already known, so it imports immediately and lands on the edit page) is a materially different flow from browsing the global Library page first (neither known yet, so it asks for both before importing). Building one modal that always asked all three questions would have added a needless step to the far more common in-project flow. |
| The sidebar "MCP Users" entry is the first *pinned* nav item gated by org role, filtered client-side in `AppSidebar` via `usePermissions()` rather than through the pre-existing `isAdmin`/`userPermission` mechanism | That mechanism only exists for *non-pinned* nav groups and checks *system*-admin permission (`authClient.admin.hasPermission`), not org owner/moderator — reusing it would have required either misusing a system-admin flag for an org-level concept or plumbing a new prop through `SideNavItems`. Filtering the one item at the `pinnedNavItems` call site was the smallest change that didn't touch that component's existing contract. |
| Deleting an `McpIdentity` cascades its resource grants and every API key issued for it, rather than blocking deletion while keys exist | Deleting a service account should kill all its credentials, not orphan them — there's no reason to keep a `ProjectApiKey` alive once the identity it represents no longer exists. |
| Activity CSV export is gated on `canManageProject` (org admin only), stricter than the read-only feed's "any project access" rule | Explicit user choice when asked — bulk-exporting the full log (including every member's activity) is a more sensitive action than viewing a live paginated feed in the UI. The summary counters stayed open to any project access, matching the feed they sit above. |
| Plan changes for existing paid subscribers call `creem.subscriptions.upgrade()` directly (new `/api/billing/change-plan` route) and write `Organization` plan/limits synchronously, instead of only relying on the async Creem webhook | The prior flow (new checkout per upgrade, hosted portal for downgrade) never referenced the existing subscription, so Creem's proration behavior was unclear/undocumented and the UI had no immediate feedback. Calling the update endpoint directly makes the local DB the source of truth for this action, with the webhook now self-correcting via live `product.id` (see next row) rather than being the only writer. |
| Webhook handlers (`onSubscriptionActive`/`onSubscriptionUpdate`/`onSubscriptionPaid`) resolve `planName` from the event's live `product.id` first, falling back to `metadata.planName` | `metadata` is set once at original checkout and neither Creem's `update` nor `upgrade` subscription endpoints can change it — so after an in-app plan change, a subsequent webhook trusting only stale metadata would silently revert the plan it just correctly set. `product.id` reflects the subscription's actual current plan regardless of which flow changed it. |
| MCP requests/month limit counts each successful call as 2 units (1 request + 1 response) and each failed call as 1 unit, rather than 1 unit per call | Explicit user requirement — "the request and the response will both be counted, together." `McpRequestLog` already stores `receivedAt`/`respondedAt` separately per row, so this is two summed `count()` queries rather than a schema change. |
| `McpRequestLog.organizationId` was added as a denormalized column (with its own index) instead of counting through the existing `projectId` → `Project.organizationId` relation | The MCP limit check runs on every single MCP request — a much hotter path than any other plan limit (which only fire on resource creation) — and the org id is already available for free from the project lookup already done in `authenticate()`, so denormalizing avoids a join on the hottest query in the app. |
| The MCP page's identities list and connection instructions were split into "MCP Users" / "Connection Instructions" tabs (`Tabs` from `@/components/ui/tabs`, first real use of that component), and a per-identity "AI instructions" markdown file (`PRIMISO.md`) was added alongside the existing `mcpServers` config JSON | User-reported gap: an AI coding agent connected via MCP had no signal to prefer Primiso's `list_resources`/`get_resource`/etc. tools over scanning local repo files. The generated `.md` (built in `src/features/mcp/utils/build-connection-instructions.ts`) is meant to be dropped at a consuming project's root next to `CLAUDE.md`/`AGENTS.md`, and is tailored per-identity from `countGrantsByType(identity.grants)` — it lists only the resource types that identity actually has grants for, per explicit user decision when asked (vs. a generic non-tailored template). Placement (tabbed, with the .md generator under the "Connection Instructions" tab) was also an explicit user decision when asked. |
