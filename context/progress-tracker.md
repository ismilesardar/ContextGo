- **Fixed the Project workspace header/nav scrolling away on long Context pages**: `ProjectWorkspaceShell` (`src/features/projects/components/project-workspace-shell.tsx`) previously tried to own its own scroll region — a plain-flow header + `ProjectWorkspaceNav`, then a `min-h-0 flex-1 overflow-y-auto` div wrapping `{children}` — under the assumption its root `flex h-full min-h-0 flex-col` div sits in a container with a real, bounded height. Fixed by dropping the internal scroll-region attempt entirely and making the header+nav block `sticky top-0 z-20` with a `bg-background` (opaque, matches `SidebarInset`'s background so scrolled content doesn't show through) instead — sticky positioning pins it to whichever ancestor actually ends up scrolling, so it no longer matters which of the nested `ScrollArea`s (outer `DashboardLayout` one vs. `PageContainer`'s own `h-[calc(100dvh-52px)]` one) is doing the work. `{children}` now renders directly, no wrapping div.

### Version history redesign: "Main" pointer model (git-branch style)

- User wanted a different mental model after seeing the first version: pick any version from a dropdown, preview it, and flag it **Main** without creating a new version number or renumbering anything — closer to moving a git branch ref than to a linear revert.
- Added `Context.mainVersionId String? @unique` + `mainVersion ContextVersion? @relation("ContextMainVersion", ...)` (and the opposite `ContextVersion.mainForContext Context? @relation("ContextMainVersion")`), decoupling "the highest version number ever created" (the `version` counter, monotonic, unaffected by Main changes) from "which version is currently active" (`mainVersionId`, a movable pointer). Pushed via `db push --accept-data-loss` (flagged only because of the new unique constraint on existing rows, which just get `NULL` — confirmed with the user before running, since the harness blocks `--accept-data-loss` without explicit approval).
- Setting a version as Main copies that snapshot's `title`/`description`/`content` onto the live `Context` row (so the app actually serves that content) and repoints `mainVersionId` — but does **not** create a new `ContextVersion` and does **not** touch `version`. A normal content edit still creates a new `ContextVersion` and *also* repoints Main at it (a fresh edit becomes active by default).
- API: `.../versions/[versionId]/restore` renamed to `.../versions/[versionId]/set-main` (same `canManageProject` gate). New `DELETE .../versions/[versionId]` with two guards, both returning 400 with a `code` field: `cannot_delete_main_version` (must set a different version as Main first — confirmed with the user: no auto-reassignment, deleting Main is always blocked) and `cannot_delete_last_version` (a Context must always keep ≥1 version). `GET .../versions` response changed from `{ versions, currentVersion }` to `{ versions, mainVersionId, latestVersion }`. `GET`/list Context endpoints now `include: { mainVersion: { select: { version: true } } }` so the UI can show the Main version's number instead of the ever-increasing counter once they diverge.
- `src/features/contexts/utils/use-contexts.ts` — `Context` gained `mainVersionId`/`mainVersion` fields; `useRestoreContextVersion` renamed `useSetMainContextVersion`; new `useDeleteContextVersion`.
- `context-version-history-modal.tsx` rewritten: a `Select` dropdown (not a scrollable row list) picks a version, its content previews below via `RichTextViewer`, and (for `canManage` users) "Set as main version" + "Delete version" buttons act on whatever's selected. Delete is disabled with a `title` tooltip when the selection is the Main version or the only version left; confirmed via a nested `CustomModal` (same pattern as `delete-context-modal.tsx`). Setting Main keeps the modal open (unlike the old auto-closing Restore) so the user sees the Main tag land on the selection.
- `context-detail-view.tsx`'s "Version {n} · View history" link and `context-card.tsx`'s `v{n}` badge both switched from `context.version` to `context.mainVersion?.version ?? context.version` (the `??` fallback covers Context rows created before this migration, which have `mainVersion: null`).

### Content format: Markdown instead of HTML

- User's reasoning: ContextGO's whole purpose is producing knowledge AI tools consume directly (per `project-overview.md`, exposed via a future MCP server/API), and AI instruction files are conventionally Markdown — the Tiptap editor built for task 003 was persisting `Context.content`/`ContextVersion.content` as HTML (`editor.getHTML()`), which isn't directly usable that way.
- Confirmed with the user before implementing: keep the exact same Tiptap WYSIWYG toolbar (no new UI, no source/rich-text toggle) — only swap what gets *saved* from HTML to Markdown; and convert all existing rows now rather than leaving mixed formats, since this is still early-stage test data.
- Added `@tiptap/markdown` (official Tiptap package, version `3.27.1` — exactly matched to the already-installed `@tiptap/react`/`@tiptap/starter-kit`/`@tiptap/pm` `^3.27.1`, superseding older community forks like `tiptap-markdown`). Its actual API differs from what a first pass assumed — checked the installed package's `.d.ts` before wiring it up rather than guessing: content is read via `editor.getMarkdown()` (not `editor.storage.markdown.getMarkdown()`), and initial content is loaded by passing `contentType: 'markdown'` to `useEditor` alongside `content: value`. There's no `html: false` config option on this version's `Markdown` extension (that was assumed from a different/older package) — dropped from the implementation.
- `src/components/editor/rich-text-editor.tsx` — added `Markdown` to the `extensions` array, `contentType: 'markdown'`, `onUpdate` now calls `onChange(editor.getMarkdown())`. Toolbar/buttons unchanged.
- `src/components/editor/rich-text-viewer.tsx` — no longer uses `dangerouslySetInnerHTML`; renders via the app's pre-existing `Markdown` component (`src/components/share/markdown.tsx`, wraps `react-markdown` + `remark-gfm`, already used elsewhere in the app) instead of introducing a new renderer.
- **One-time data migration**: wrote a throwaway script at the repo root (`migrate-content-to-markdown.ts`, using `turndown` — a standalone HTML→Markdown converter chosen specifically because it runs in plain Node with no DOM/editor instance needed, unlike driving Tiptap server-side) that converted every existing `Context.content` and `ContextVersion.content` from HTML to Markdown via the real `prisma` client (relative imports, not `@/` aliases, since `tsx` doesn't resolve `tsconfig.json` paths by default). Ran once via `pnpm dlx tsx migrate-content-to-markdown.ts` (1 Context + 3 versions converted at the time), spot-checked the output was valid Markdown, then deleted the script — it was never meant to be a permanent part of the codebase. `turndown`/`@types/turndown` stay installed as regular/dev dependencies even though the script is gone, in case a similar one-off conversion is needed again later (e.g. for a future resource type migrating off a different format).
- No Prisma schema change — `content` stayed `String @db.Text` on both models throughout; only what's semantically inside that string changed. No `db push`/`generate` needed for this change, but the dev server was still restarted afterward (new dependencies + a shared component change).

## Architecture Decisions

| Decision | Reason |
|----------|--------|
| Projects are per-project ACL (`ProjectMember`), not just workspace-role-gated | User feedback: a project must be invisible to a workspace member until explicitly granted access, so workspace `member`/`viewer` roles alone aren't enough. |
| Org `owner`/`moderator` implicitly bypass `ProjectMember` and see all projects | Standard admin override — avoids needing to backfill `ProjectMember` rows for every project whenever an org admin needs access. |
| Project write authorization is enforced inline via `src/lib/permissions/project-access.ts`, not by extending Better Auth's access-control statements | Keeps `src/lib/permissions/workspace-permissions.ts` and `src/lib/auth/auth.ts` untouched, per the task's "do not rebuild auth" constraint. |
| Used `prisma db push` instead of `prisma migrate dev` for the new models | This project has no `prisma/migrations` history (schema was managed via `db push`); running `migrate dev` for the first time would have required a full database reset, which risks dropping existing data. `db push` applies the new tables additively without that risk. |
| Projects list is a card grid, not a data table | Matches the plan's chosen UX (Linear/Notion-style) for a small number of top-level entities that are primarily "click to open," vs. the dense row-based `MemberTable` pattern used for workspace members. |
| **(Supersedes the first row above)** Project management (create, settings, member management, and — once built — asset creation inside a project) is now gated on org-level `owner`/`moderator` only, not per-project delegated ownership | Explicit user requirement: "No one except the owner and moderator of the organization will be able to create projects... access settings... create assets." `canManageProject()` in `project-access.ts` now checks `isOrgAdmin` instead of `role === 'owner'`. `ProjectMember.role` `'owner'` is retired as an assignable value (Zod enums narrowed to `member`\|`viewer`); read-level `ProjectMember` access (a project is invisible until granted) is unchanged — this only tightens *management*, not visibility. **Important for future work**: when Contexts/Instructions/Skills/etc. get real CRUD (currently `PlaceholderTab` stubs), asset creation inside a project must also be gated on `isOrgAdmin`/`canManageProject`, per this same requirement — don't default to allowing any project member to create assets. |
